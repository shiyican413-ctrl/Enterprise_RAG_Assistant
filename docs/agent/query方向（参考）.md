# query改写

RAG系统Query改写技术全解析 笔记 一、什么是 Query 改写 1. 定义：用户原始提问存在模糊、简短、歧义、信息缺失等问题，通过 AI 大模型对原始查询进行扩充、修正、拆分、同义转换，生成更适配向量库检索的标准化问句，提升 RAG 召回文档准确率。2. 核心作用 - 解决用户口语化、碎片化提问- 消除一词多义歧义- 补充隐含背景信息- 拆分复合多问题，避免检索遗漏- 适配向量模型语义匹配逻辑 二、原始 Query 常见缺陷 1. 过短极简：仅关键词，无上下文（例：“RAG 优化”）2. 口语化表达：网络用语、省略主语、倒装句3. 多问题混杂：一句话包含多个独立诉求4. 歧义词汇：一词多义，知识库无法精准匹配5. 信息缺失：缺少限定条件、场景、业务范围6. 反向提问：否定式问句，向量检索易跑偏 三、主流 Query 改写技术分类 1. 同义扩展改写（基础版） - 原理：基于同义词、近义词、行业术语扩充查询- 实现方式：提示词指令、词向量聚类、行业词库映射- 适用场景：专业名词简写、缩写、俗称转换- 示例：原句 “向量召回慢”→改写 “RAG 向量数据库检索速度慢的原因与优化方案” 2. 子问题拆分改写（多轮检索） - 原理：把复合长问句拆解为多个独立子 Query，分别检索再合并文档- 优势：每个子问题精准匹配对应知识库片段，避免单条 query 覆盖不全- 示例：原句 “RAG 的 Query 改写和重排序怎么做，各自有什么优缺点”拆分两条子查询：① RAG 系统 Query 改写实现方法② RAG 重排序技术实现方案③ Query 改写与重排序优缺点对比 3. 上下文补全改写（对话 RAG 专用） - 针对多轮对话场景，结合历史对话补充缺失指代、前文背景- 解决代词歧义：它、这个、上文说的、前文提到的模型- 流程：历史对话 + 当前 query 输入大模型，生成完整独立问句 4. 反向 / 否定句式正向转换 用户提问带否定词，向量库难匹配，转为正向需求例：“RAG 哪些做法不能提升召回精度”→改写 “提升 RAG 检索精度的有效方案，排除无效优化手段” 5. 多角度生成 Query（多路召回） 同一原始问题生成多条不同表述 Query，并行检索，融合结果思路：同义改写 + 场景限定 + 不同提问句式，多路召回提升覆盖度 6. 纠错改写 修正错别字、专业术语写错、逻辑不通的用户提问，标准化术语 四、Query 改写工程落地实现方案 方案 1：Prompt 模板驱动（轻量化，中小模型可用） 固定结构化提示词约束大模型输出改写规则，无需微调，开箱即用标准提示词核心指令： 1. 识别用户问题是否存在歧义、信息缺失、多问题2. 补充行业背景，完善模糊表述3. 拆分复合问题为独立子查询4. 生成 3 条不同语义表述的检索问句5. 仅输出改写后的查询列表，无多余解释 方案 2：微调专用 Query 改写小模型（高并发场景） - 数据集：用户真实提问 + 人工标注优质改写样本- 优势：速度快、成本低于每次调用大模型、适合高并发线上 RAG 服务- 劣势：需要标注数据，维护成本更高 方案 3：规则引擎 + 大模型混合 简单短 query 用词典 / 正则规则快速改写；复杂歧义、长对话 query 交给大模型处理，平衡成本与效果 五、Query 改写在完整 RAG 链路中的位置 完整链路：用户提问 → Query 改写模块 → 多路向量检索 → 文档召回 → 重排序 Rerank → 上下文拼接 → LLM 生成回答改写是检索前预处理核心步骤，直接决定召回文档质量，是低成本提升 RAG 效果的关键手段。 六、实操优缺点 优点 1. 显著提升低质量口语化提问的召回准确率2. 多路改写召回，扩大相关文档覆盖范围3. 解决对话上下文指代模糊问题4. 无需改动向量库、嵌入模型，改造成本低 缺点 1. 过度改写会引入无关语义，造成噪声召回2. 每次调用大模型改写会增加接口耗时与 token 成本3. 拆分过多子查询会提升数据库检索并发压力 七、落地优化避坑要点 1. 增加长度限制：改写后 query 不宜过长，避免向量语义稀释2. 过滤重复 Query：多路生成后去重，减少重复检索3. 阈值控制：简单短问题不做过度扩充，复杂歧义问题加强改写4. 缓存机制：高频重复用户提问缓存改写结果，减少重复调用大模型5. 结果校验：改写后简单校验是否偏离用户原始核心诉求，过滤跑偏问句 八、适用业务场景 1. 企业知识库问答、内部文档 RAG 机器人2. 客服对话机器人（多轮对话高频模糊提问）3. 行业垂直大模型（专业术语多、用户表述不标准）4. 本地文档检索、私有知识库问答系统
