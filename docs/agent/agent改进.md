# 企业级agent开发框架

这套架构里，**不是每一层都要用大模型**。企业里通常遵循一句话：

> **需要“理解、判断、生成”的地方用大模型；需要“权限、执行、记录、校验”的地方不要交给大模型。**

对应你这张图：

```
用户
 ↓
入口层 / API / 权限校验
 ↓
Router / Planner
 ↓
Workflow / Agent Runtime / Executor
 ↓
受控 ReAct Agent / Tool-calling Agent
 ↓
Tools / RAG / 数据库 / 内部系统
 ↓
结果聚合 / 审计 / 日志 / 评估
```

---

## 1. 用户输入层：可用大模型，但不是必须

用户发来的问题可能很乱，比如：

```
帮我看看客户这个问题咋处理
```

这里可以用大模型做：

```
意图识别
问题改写
补全上下文
提取结构化参数
判断是否需要追问
```

例如把用户问题变成：

```json
{
  "intent": "customer_support",
  "need_search_order": true,
  "need_rag": true,
  "risk_level": "normal"
}
```

但这层也可以不用大模型，用规则、关键词、传统分类模型都行。

---

## 2. 入口层 / API / 权限校验：不要用大模型做核心判断

这一层主要负责：

```
用户是谁
有没有登录
是什么角色
能不能访问这个接口
能不能看这个知识库
能不能查这个客户数据
```

这里**不能让大模型决定权限**。

错误做法：

```
让大模型判断：这个用户能不能看 HR 薪资文档？
```

正确做法：

```
后端系统根据 user_id / role / department / permission 表判断
```

大模型最多辅助做：

```
识别用户请求是否涉及敏感内容
判断是否可能越权
生成拒绝话术
```

但真正的权限判断必须是代码和数据库。

---

## 3. Router / Planner：经常用大模型

这一层是最适合用大模型的地方之一。

它负责：

```
判断任务类型
选择走哪个流程
拆解步骤
决定要不要检索
决定要不要调用工具
决定使用哪个 Agent
```

例如用户问：

```
帮我分析一下这个客户为什么流失
```

Planner 可以拆成：

```
1. 查询客户基本信息
2. 查询最近沟通记录
3. 查询订单变化
4. 检索知识库里的流失原因模板
5. 总结原因和建议
```

也就是：

```
Router / Planner = 大模型常用
```

但企业里一般会要求它输出结构化结果，例如 JSON，而不是随便写一段话。

---

## 4. Workflow / Agent Runtime / Executor：核心不要用大模型

这一层是“执行中枢”。

它负责：

```
按步骤执行
控制最大轮数
控制超时
失败重试
记录日志
合并结果
控制成本
处理 fallback
```

这里一般**不应该让大模型自由决定**。

比如这些事情应该由代码控制：

```python
max_steps = 5
timeout = 30
allowed_tools = ["search_docs", "query_order", "summarize"]
retry = 2
```

大模型可以参与某些局部判断，比如：

```
当前结果是否足够？
是否需要进入人工审核？
这一步失败后是否换一种查询方式？
```

但 Runtime 本身应该是确定性的。

你之前说的 `executor.py` 就属于这一层。它不是负责“聪明”，而是负责“稳”。

---

## 5. 受控 ReAct Agent / Tool-calling Agent：大量使用大模型

这一层就是大模型最核心的使用位置。

ReAct Agent 会做：

```
看当前问题
判断下一步调用哪个工具
生成工具参数
读取工具返回结果
判断结果够不够
不够继续调用工具
最后生成答案
```

比如：

```
Thought: 我需要先查订单
Action: query_order(customer_id=123)

Observation: 最近 30 天订单下降 70%

Thought: 还需要查沟通记录
Action: search_crm_logs(customer_id=123)
```

所以：

```
ReAct Agent / Tool-calling Agent = 必须用大模型
```

但注意，是**受控大模型**，外面要有限制：

```
最多调用几次
能调用哪些工具
不能越权访问
参数要校验
结果要记录
```

---

## 6. Tools / RAG / 数据库 / 内部系统：大多数不用大模型

工具层本身一般不用大模型。

比如：

```
查数据库
调用订单 API
调用 CRM
查库存
查知识库
执行 SQL
发送邮件
创建工单
```

这些都应该是确定性代码。

但是 RAG 里面有几个地方会用大模型：

```
Query Rewrite：改写用户问题
Embedding：向量化
Rerank：重排检索结果
Answer Generation：基于资料生成答案
```

注意：Embedding 模型也算模型，但不一定是聊天大模型。

RAG 标准流程一般是：

```
用户问题
 ↓
大模型改写问题，可选
 ↓
Embedding 检索
 ↓
Rerank 重排，可选
 ↓
拿到文档片段
 ↓
大模型基于片段回答
```

所以：

```
数据库查询本身不用大模型
RAG 检索前后会用大模型
```

---

## 7. 结果聚合：经常用大模型

当多个工具返回很多结果时，需要整理成用户能看懂的答案。

比如工具返回：

```
订单数据
客服记录
知识库片段
用户画像
历史工单
```

大模型适合做：

```
总结
归纳
解释
生成自然语言答案
转成报告
生成表格
给出建议
```

例如：

```
客户流失主要有三个原因：
1. 最近两次投诉未及时处理
2. 竞品价格更低
3. 客户高频功能长期未上线
建议优先安排客户成功经理回访。
```

所以结果聚合层经常用大模型。

---

## 8. 审计 / 日志：不要用大模型做基础记录

日志和审计要靠系统记录。

比如：

```
谁在什么时候问了什么
调用了哪个工具
查了哪个数据库
返回了哪些 source
花了多少 token
耗时多少
有没有失败
```

这些不能靠大模型记，必须靠代码写入日志系统。

大模型可以辅助做：

```
异常日志总结
失败原因分析
风险摘要
质检报告
```

但原始日志必须真实、完整、不可篡改。

---

## 9. 评估：可以用大模型，但不能只靠大模型

评估分两类。

### 确定性评估，不用大模型

比如：

```
答案有没有引用 source
有没有超时
有没有越权调用工具
JSON 格式对不对
SQL 有没有危险操作
是否命中敏感词
```

这些用规则和代码。

### 语义评估，可以用大模型

比如：

```
回答是否解决用户问题
是否忠实于文档
有没有幻觉
语气是否合适
建议是否合理
```

这里可以用大模型当 judge。

但企业里不会完全相信 judge，一般会结合：

```
规则评估 + 人工抽检 + 大模型评估
```

---

# 最清楚的对应表

| 架构层                           | 是否用大模型 | 主要作用                       |
| ----------------------------- | ------ | -------------------------- |
| 用户输入理解                        | 可用     | 意图识别、问题改写、参数抽取             |
| API / 登录 / 权限                 | 不建议    | 必须由后端代码和权限系统控制             |
| Router / Planner              | 常用     | 任务分类、流程选择、步骤拆解             |
| Workflow / Runtime / Executor | 核心不用   | 控制执行、超时、重试、日志、成本           |
| ReAct / Tool-calling Agent    | 必用     | 多轮工具调用、动态决策                |
| Tools / 数据库 / 内部系统            | 不用     | 真正执行动作、查数据、调用 API          |
| RAG                           | 部分使用   | 改写、Embedding、Rerank、基于资料回答 |
| 结果聚合                          | 常用     | 总结、解释、生成最终答案               |
| 审计 / 日志                       | 基础不用   | 系统记录；大模型只做日志分析             |
| 评估                            | 部分使用   | 规则评估 + LLM judge + 人工抽检    |

---

# 简化成一句架构原则

```
LLM 负责：
理解、规划、判断、生成、总结

代码负责：
权限、执行、限制、校验、记录、重试
```

---

所以你这套架构里，真正强依赖大模型的是这几块：

```
Router / Planner
受控 ReAct Agent
RAG 问答生成
结果聚合
语义评估
```

不应该交给大模型的是：

```
权限校验
工具实际执行
数据库访问控制
Runtime 执行规则
日志审计
成本限制
安全拦截
```

你可以这样理解企业级 Agent：

> **大模型是大脑，但不是老板；Runtime 才是老板。**S
