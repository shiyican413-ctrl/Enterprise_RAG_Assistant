# 登录权限与知识库访问控制方案

## 1. 目标定位

`Enterprise RAG Assistant` 的目标是企业级 RAG 知识库平台，因此登录、权限和知识库访问控制不能只做页面级隐藏，而要贯穿：

- 用户身份认证
- 接口鉴权
- 角色权限控制
- 知识库空间隔离
- 文档级访问控制
- Milvus 检索过滤
- 会话历史隔离
- 操作审计和风险控制

建议分阶段实现：先做能跑通业务闭环的 MVP 权限，再演进到企业级 RBAC、空间隔离、审计和配额治理。

## 2. 当前状态

当前后端接口基本是匿名开放：

| 接口 | 当前风险 |
| --- | --- |
| `POST /api/documents/upload` | 任意人可上传文档 |
| `GET /api/documents` | 任意人可查看全部文档 |
| `DELETE /api/documents/{document_id}` | 任意人可删除文档 |
| `POST /api/documents/batch-delete` | 任意人可批量删除 |
| `GET /api/documents/{document_id}/chunks` | 任意人可查看文档片段全文 |
| `POST /api/knowledge/rebuild` | 任意人可重建知识库 |
| `POST /api/chat/ask` | 任意人可调用模型和检索知识库 |
| `POST /api/chat/stream` | 任意人可流式调用模型 |
| `GET /api/chat/conversations/{conversation_id}` | 只要知道 ID 就可能读取会话 |

后续权限设计要解决三个核心问题：

1. 谁可以登录系统。
2. 登录后可以看哪些知识库、文档和会话。
3. 调用问答时只能检索自己有权限的知识范围。

## 3. 权限模型总览

建议采用企业常见的四层模型：

```text
User 用户
  -> Role 角色
  -> Workspace / Knowledge Space 知识库空间
  -> Document 文档 / Chunk 片段
```

权限判断不要只依赖前端菜单，而要在后端每个敏感接口执行。

### 3.1 角色分层

第一阶段先用固定角色，后续再做可配置权限点。

| 角色 | 定位 | 核心权限 |
| --- | --- | --- |
| `viewer` 普通员工 | 查询企业知识 | 问答、查看允许范围内的文档摘要 |
| `maintainer` 知识库维护员 | 维护资料 | 上传、查看片段、重建自己负责的知识库 |
| `admin` 管理员 | 平台管理 | 用户、角色、知识库、删除、审计、全局配置 |
| `auditor` 审计员 | 安全审查 | 查看日志、调用记录、引用记录，不改数据 |

MVP 可以只实现：

- `viewer`
- `maintainer`
- `admin`

### 3.2 权限点设计

后续企业级版本建议把权限拆成权限点：

| 权限点 | 说明 |
| --- | --- |
| `chat:ask` | 发起问答 |
| `chat:read_own` | 查看自己的会话 |
| `chat:read_all` | 查看所有会话 |
| `document:list` | 查看文档列表 |
| `document:read` | 查看文档详情和片段 |
| `document:upload` | 上传文档 |
| `document:delete` | 删除文档 |
| `document:batch_delete` | 批量删除文档 |
| `knowledge:rebuild` | 重建知识库 |
| `knowledge:search_test` | 调试检索结果 |
| `audit:read` | 查看审计日志 |
| `user:manage` | 管理用户和角色 |

MVP 可以先把权限点写死在代码里，后续再落库。

## 4. 数据模型规划

### 4.1 MVP 数据表

建议先在 PostgreSQL 中新增：

```text
users
roles
user_roles
knowledge_spaces
space_members
document_acl
audit_logs
```

MVP 最小化可以先不做 `roles` 和 `user_roles` 表，直接在 `users.role` 里存固定角色。

#### users

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uuid | 用户 ID |
| `email` | text | 登录账号 |
| `name` | text | 显示名称 |
| `password_hash` | text | 密码哈希 |
| `role` | text | `viewer/maintainer/admin` |
| `department` | text | 部门 |
| `is_active` | bool | 是否启用 |
| `created_at` | timestamptz | 创建时间 |
| `last_login_at` | timestamptz | 最近登录 |

#### knowledge_spaces

| 字段 | 类型 | 说明 |
| --- | --- | --- |

#### space_members

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `space_id` | uuid | 知识库空间 |

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `document_id` | text | Milvus 文档 ID |
| `subject_type` | text | `user/role/department` |

#### audit_logs

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uuid | 日志 ID |
| `actor_user_id` | uuid | 操作人 |
| `action` | text | 操作类型 |
| `resource_type` | text | `document/chat/knowledge/user` |
| `resource_id` | text | 资源 ID |
| `ip_address` | text | IP |
| `user_agent` | text | UA |
| `metadata` | jsonb | 附加信息 |
| `created_at` | timestamptz | 时间 |

### 4.2 Milvus 字段扩展

当前 Milvus collection 已存：

```text
document_id
document_name
chunk_index
content
metadata_json
created_at
embedding
embedding_model
```

为了权限过滤，建议增加标量字段：

```text
space_id
owner_user_id
department
visibility
acl_tags
```

检索时通过 Milvus filter expression 限制范围：

```text
space_id in ["space_a", "space_b"] and visibility in ["internal", "public"]
```

如果后续要支持更复杂的文档级 ACL，不建议把所有 ACL 都塞进 Milvus；Milvus 只放可过滤字段，复杂权限在 PostgreSQL 先算出允许的 `space_id/document_id`，再传给 Milvus 过滤。

## 5. 后端实现方案

### 5.1 认证方式

MVP 建议使用：

```text
邮箱 + 密码登录
JWT access token
可选 refresh token
```

接口：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/auth/login` | 登录，返回 access token |
| `POST` | `/api/auth/logout` | 登出，MVP 可前端清 token |
| `GET` | `/api/auth/me` | 获取当前用户 |
| `POST` | `/api/auth/change-password` | 修改密码 |

密码哈希使用：

```text
passlib[bcrypt] 或 argon2-cffi
```

JWT 建议字段：

```json
{
  "sub": "user_id",
  "email": "user@example.com",
  "role": "maintainer",
  "exp": 1234567890
}
```

### 5.2 FastAPI 依赖设计

新增：

```text
backend/ai_service/security/
  auth_service.py
  password_service.py
  jwt_service.py
  permissions.py
  dependencies.py
```

核心依赖：

```python
get_current_user()
require_permission("document:upload")
require_role("admin")
get_allowed_space_ids(user)
```

使用方式：

```python
@router.post("/api/documents/upload")
async def upload_document(
    file: UploadFile = File(...),
    current_user: User = Depends(require_permission("document:upload")),
):
    ...
```

### 5.3 接口权限矩阵

| 接口 | viewer | maintainer | admin | 规则 |
| --- | --- | --- | --- | --- |
| `GET /api/documents` | 是 | 是 | 是 | 只返回有权限空间 |
| `GET /api/documents/{id}/chunks` | 部分 | 是 | 是 | viewer 只能读有权限文档 |
| `POST /api/documents/upload` | 否 | 是 | 是 | 上传时必须指定 `space_id` |
| `DELETE /api/documents/{id}` | 否 | 部分 | 是 | maintainer 只能删自己空间 |
| `POST /api/documents/batch-delete` | 否 | 部分 | 是 | 每个文档逐个校验 |
| `POST /api/knowledge/rebuild` | 否 | 部分 | 是 | MVP 可以仅 admin |
| `POST /api/chat/ask` | 是 | 是 | 是 | 检索范围按用户过滤 |
| `POST /api/chat/stream` | 是 | 是 | 是 | 同上 |
| `GET /api/chat/conversations/{id}` | 自己 | 自己 | 全部 | conversation 绑定 user_id |

### 5.4 知识库调用限制

问答接口不能只判断用户是否登录，还要控制检索范围。

#### MVP 规则

1. 用户登录后获取 `allowed_space_ids`。
2. 上传文档必须选择一个 `space_id`。
3. 文档入 Milvus 时写入 `space_id`。
4. 问答检索时传入过滤条件：

```python
vector_store.search(
    query=question,
    top_k=top_k,
    filters={
        "space_ids": allowed_space_ids,
    },
)
```

5. Milvus 查询时拼接表达式：

```text
space_id in ["..."]
```

6. sources 返回前再做一次后端权限校验，防止过滤条件错误导致越权。

#### 企业级规则

后续检索过滤建议叠加：

```text
tenant_id
space_id
department
document_status
classification_level
valid_from / valid_to
```

典型表达：

```text
tenant_id == "t1"
and space_id in ["hr", "finance"]
and status == "active"
and classification_level <= 2
```

### 5.5 会话历史隔离

`chat_turns` 建议新增：

```text
user_id
tenant_id
space_ids
```

规则：

- 普通用户只能读取自己的会话。
- 管理员可以按审计权限读取全部或指定空间会话。
- 会话保存 sources 时，需要保存当时的权限上下文，便于审计。
- 如果用户权限被撤销，历史 sources 是否可见要有策略：
  - 严格模式：实时重新校验，撤权后不可见。
  - 审计模式：保留回答，但隐藏引用详情。

MVP 建议采用严格模式。


```text

```

如果使用纯前端存 token，MVP 可放 `localStorage`；企业级更建议后端设置 `HttpOnly Secure SameSite` cookie。

### 6.3 API 调用改造

当前 `lib/api.ts` 所有 fetch 都没有 token。需要统一封装：

```typescript
export async function apiFetch(path: string, init?: RequestInit) {
  return fetch(`${API_BASE_URL}${path}`, {
    ...init,
    headers: {
      ...init?.headers,
      Authorization: `Bearer ${getAccessToken()}`,
    },
  });
}
```

所有接口改用 `apiFetch`。

## 7. 分阶段实施路线

### 阶段 1：MVP 登录与基础角色

目标：所有核心接口不再匿名开放。

后端：

- 新增 `users` 表。
- 新增密码哈希和 JWT。
- 新增 `/api/auth/login`、`/api/auth/me`。
- 增加 `get_current_user` 依赖。
- 给文档、知识库、聊天接口加登录校验。
- 会话写入 `user_id`。
- 普通用户只能读取自己的会话。

前端：

- 新增 `/login`。
- 登录后保存 token。
- API 请求自动带 `Authorization`。
- 未登录跳转登录页。
- 顶栏用户图标显示当前用户。

验收标准：

- 未登录访问 `/api/chat/stream` 返回 401。
- 登录后可以问答。
- 未登录不能上传、删除、重建。
- 用户 A 不能读取用户 B 的会话。

### 阶段 2：角色权限与知识库维护员

目标：区分普通查询用户和知识库维护用户。

后端：

- `users.role` 支持 `viewer/maintainer/admin`。
- 新增权限判断函数。
- 上传、删除、批量删除、重建加角色限制。
- 审计记录上传、删除、重建、登录失败。

前端：

- 根据角色隐藏/禁用操作按钮。
- 删除、重建等危险操作保留确认弹窗。
- 权限不足时展示 403 文案。

验收标准：

- viewer 可以问答，但不能上传删除。
- maintainer 可以上传和删除文档。
- admin 可以执行全部管理操作。

### 阶段 3：知识库空间隔离

目标：用户只能检索授权知识库空间。

后端：

- 新增 `knowledge_spaces`、`space_members`。
- 文档上传必须带 `space_id`。
- Milvus collection 增加 `space_id` 字段。
- `list_documents` 按 `space_id` 过滤。
- `search` 按 `allowed_space_ids` 过滤。
- sources 返回前二次校验权限。

前端：

- 增加知识库空间选择器。
- 文档列表按空间筛选。
- 问答页可选择“全部可访问知识库”或指定空间。

验收标准：

- 用户 A 只属于 HR 空间，问财务空间问题时无法检索到财务文档。
- 文档列表只展示自己空间文档。
- 管理员可切换查看所有空间。

### 阶段 4：文档级权限与敏感等级

目标：支持更细粒度的企业安全要求。

后端：

- 新增 `document_acl`。
- 文档 metadata 增加 `classification_level`。
- 用户增加 `clearance_level` 或部门属性。
- 检索前计算 allowed document IDs 或 allowed filters。
- sources 中敏感字段按权限脱敏。

前端：

- 文档上传时选择密级。
- 文档详情展示可见范围。
- 无权限文档不可查看片段全文。

验收标准：

- 同一知识库空间下，不同密级文档可被不同用户检索。
- 无权限用户不会看到片段内容和引用详情。

### 阶段 5：企业级审计、配额和治理

目标：可运营、可排查、可合规。

后端：

- 完整 `audit_logs`。
- 记录问答 trace、检索文档、命中文档、模型、token、耗时。
- 用户级/空间级调用限额。
- 上传文件大小、类型、频率限制。
- 敏感词和越权检索告警。
- 管理员可禁用用户或知识库空间。

前端：

- 审计日志页面。
- 调用统计页面。
- 知识库质量页面。
- 权限变更历史。

验收标准：

- 可追踪“谁在什么时候问了什么，检索了哪些文档，返回了哪些引用”。
- 超出配额后接口返回明确错误。
- 管理员能停用用户、撤销空间权限。

## 9. 推荐先做的最小版本

如果下一步开始实现，建议第一轮只做这些：

1. `users` 表，内置一个 admin 初始用户。
2. `/api/auth/login` 和 `/api/auth/me`。
3. JWT 鉴权。
4. 所有 `/api/documents/*`、`/api/knowledge/*`、`/api/chat/*` 加登录校验。
5. `users.role` 固定三种角色。
6. viewer 只能问答和看文档，不能上传删除。
7. maintainer 可以上传、删除、重建。
8. admin 全部权限。
9. `chat_turns` 写入 `user_id`，会话只能本人读取。
10. 前端加登录页和 token 自动附带。

这个版本能快速把系统从“匿名工具”升级为“有企业权限雏形的平台”。后面再做知识库空间和 Milvus 过滤，会比较稳。

## 10. 关键风险

- 只做前端隐藏按钮没有安全意义，后端必须鉴权。
- 问答接口必须做知识库范围过滤，否则用户能通过提问间接读取无权限文档。
- sources 返回前要二次校验权限，避免检索过滤配置错误造成泄露。
- 会话历史必须绑定 `user_id`，不能只靠 `conversation_id`。
- 管理员和维护员的删除、重建操作必须写审计日志。
- Milvus 字段变更涉及 collection schema，已有 collection 可能需要迁移或重建。
- 上传原始文件 `data/uploads` 也需要权限和清理策略，否则删除索引不等于删除源文件。
