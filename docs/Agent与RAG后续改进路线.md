# Agent 与 RAG 后续改进路线

本文档用于记录 `Enterprise RAG Assistant` 后续从“可运行的企业 RAG Agent”演进到“可治理、可评测、可审计的企业智能体平台”的改进方向。

当前项目已经具备基础能力：

- 文档上传、解析、切分、向量化入库
- Milvus 向量检索
- RAG 问答与引用来源返回
- Planner、Executor、ReAct Agent 分层
- Tool Registry 工具注册机制
- SSE 流式输出与 agent_step 展示
- Trace 路由耗时记录
- PostgreSQL 会话记录

所以后续不需要推倒重来，重点是把现有能力做准、做稳、做可控。

## 1. 当前系统的大白话判断

现在系统已经像一个“会查资料、会回答、会展示过程的智能助手”。

但它还不是一个真正成熟的企业 Agent 平台，主要差在：

- 找资料还不够准
- 工具调用还不够规范
- Agent 推理还比较依赖 Prompt 约束
- 没有系统化评测来判断回答质量
- 安全、权限、审计还没有贯穿全链路
- 多 Agent 还不适合急着上

一句话总结：

> 当前方向是对的，下一步不是堆更多炫酷 Agent，而是先把检索准确率、工具规范、安全护栏、评测体系和审计能力补起来。

## 2. 优先级最高的改进

### 2.1 提升检索准确率

当前主要依赖向量相似度检索。向量检索适合语义匹配，但企业知识库里经常有制度编号、产品型号、人名、部门、流程节点、金额、日期等精确关键词，只靠向量检索容易漏。

建议升级为：

```text
用户问题
  -> 查询改写
  -> 向量检索 dense search
  -> 关键词/BM25 检索 sparse search
  -> 多路结果融合
  -> rerank 重排序
  -> 返回最可信证据
  -> 生成答案
```

建议新增能力：

- 混合检索：dense embedding + sparse/BM25
- Rerank：对召回片段重新排序
- Query rewrite：把用户问题改写成更适合检索的查询
- Metadata filter：按知识库、部门、标签、文档类型、权限范围过滤
- 引用命中统计：记录每次回答真正用了哪些片段

第一阶段可以先做：

- 保留现有 Milvus dense 检索
- 增加本地 BM25 或稀疏检索
- 增加一个 rerank 层
- 在前端知识库页面展示检索得分和重排序结果

### 2.2 建立 RAG 评测体系

现在系统能回答问题，但还缺一个“考试系统”判断质量。

后续每次改检索、改 Prompt、换模型，都应该能回答这些问题：

- 回答是否基于资料？
- 有没有乱编？
- 引用文档是否正确？
- 召回的片段是否真的相关？
- 新版本是否比旧版本更好？

建议新增 `evals/` 目录，维护固定评测集：

```text
evals/
  questions.jsonl
  expected_sources.jsonl
  run_eval.py
  reports/
```

每条评测数据包含：

- 用户问题
- 期望答案要点
- 期望命中文档
- 期望命中片段
- 是否允许使用通用知识
- 最低引用数量

建议评测指标：

- 召回命中率
- 引用准确率
- 回答忠实度
- 回答相关性
- 无资料时是否正确拒答
- 平均响应耗时
- 单次回答成本

### 2.3 把工具调用做规范

当前工具层已经有 `ToolRegistry` 和 `KnowledgeSearchTool`，这是一个好基础。

后续工具不应该只是一个名字和描述，而应该变成企业可治理的工具协议。

每个工具建议增加：

- 输入 JSON Schema
- 输出 JSON Schema
- 权限要求
- 是否需要人工确认
- 超时时间
- 重试策略
- 是否允许写操作
- 是否记录审计日志
- 敏感字段脱敏规则

例如：

```text
knowledge_search
  类型：只读工具
  权限：需要 knowledge:read
  输入：query, top_k, filters
  输出：sources, raw_results
  审计：记录用户、问题、命中文档、耗时

ticket_create
  类型：写入工具
  权限：需要 ticket:create
  输入：title, description, priority
  输出：ticket_id, status
  审计：必须记录
  人工确认：建议开启
```

MCP 适合做外部工具接入标准。当前项目已有 MCP adapter 预留，后续可以把内部业务系统工具通过 MCP 或统一 adapter 接进来。

### 2.4 升级 Agent 执行方式

当前 Agent 是 Prompt-based ReAct：让模型按 JSON 格式输出 action 或 final，再由代码解析。

优点：

- 简单
- 模型无关
- 当前可运行

缺点：

- 模型可能不按 JSON 输出
- 工具参数不够严格
- 状态恢复能力弱
- 复杂流程不好维护

后续建议分两步升级：

第一步：保留现有架构，增加结构化输出校验。

- 对 action_input 做 schema 校验
- JSON 解析失败时自动修复一次
- 限制工具白名单
- 工具异常统一返回可解释 observation

第二步：引入状态图执行。

可以参考 LangGraph 这类状态图思路，把流程显式拆成节点：

```text
guardrails
  -> memory_load
  -> planner
  -> retrieval
  -> rerank
  -> agent_reasoning
  -> answer_generation
  -> citation_check
  -> memory_save
```

这样后续更容易做：

- 失败重试
- 中断恢复
- 人工审批
- 节点级观测
- 节点级测试
- 不同业务流程分支

### 2.5 加强安全护栏

当前 Guardrail 主要检查空输入和长度。企业级还需要更完整的安全链路。

建议增加：

- Prompt injection 检测
- 越权问题识别
- 敏感信息检测与脱敏
- 无权限文档过滤
- sources 返回前二次权限校验
- 工具调用前权限校验
- 写操作工具人工确认
- 输出答案引用校验

特别是问答接口不能只在前端隐藏菜单，后端必须做权限过滤。

### 2.6 加强可观测性和审计

当前 Trace 已经记录每一步耗时，后续可以继续扩展成企业级观测数据。

建议记录：

- trace_id
- user_id
- conversation_id
- question
- plan
- route steps
- 检索耗时
- rerank 耗时
- 命中文档
- 工具调用参数
- 工具调用结果摘要
- 模型名称
- token 用量
- 成本
- 错误信息
- 用户反馈

这些数据后续可以支持：

- 问题排查
- 检索质量分析
- 成本统计
- 权限审计
- 用户行为分析
- 版本效果对比

## 3. 不建议马上做的事

### 3.1 不急着上多 Agent

多 Agent 听起来很强，但企业 RAG 第一阶段不建议急着拆很多 Agent。

原因：

- 成本会上升
- 延迟会上升
- 调试难度会上升
- 每个 Agent 的责任边界容易混乱
- 评测更复杂

建议先把单 Agent 做稳定，再考虑拆分：

```text
第一阶段：单 Agent + 工具治理 + 评测
第二阶段：增加审核节点和人工确认
第三阶段：再拆检索 Agent、回答 Agent、审核 Agent、业务工具 Agent
```

### 3.2 不急着重构全部框架

当前项目已有清晰分层，不需要为了追新框架大改。

建议渐进式演进：

- 先补检索质量
- 再补评测
- 再补工具 schema
- 再补状态图
- 最后考虑多 Agent

## 4. 推荐实施路线

### 阶段一：先把 RAG 做准

目标：让系统更会找资料，少乱答。

建议任务：

- 增加 BM25 或 sparse 检索
- 增加 rerank 层
- 增加 query rewrite
- 增加引用校验
- 增加无资料拒答策略
- 建立第一版评测集

验收标准：

- 常见制度问题能命中正确文档
- 答案能带正确引用
- 无资料问题不会硬编
- 每次改动可以跑评测对比

### 阶段二：把 Agent 做稳

目标：让 Agent 的每一步更可控。

建议任务：

- 工具输入输出 schema 化
- 工具调用权限校验
- 工具超时和重试
- JSON 输出修复与校验
- Agent 执行失败降级
- 前端展示工具调用详情

验收标准：

- 工具参数错误不会导致系统崩溃
- Agent 不会调用未授权工具
- 工具调用过程可追踪
- 异常时用户能看到合理提示

### 阶段三：补企业治理能力

目标：让系统可以进入企业真实场景。

建议任务：

- 登录认证
- RBAC 权限
- 文档级权限过滤
- sources 二次权限校验
- 审计日志
- 敏感字段脱敏
- 成本和 token 统计

验收标准：

- 用户只能检索自己有权限的知识
- 管理员能查上传、删除、问答、工具调用日志
- 敏感资料不会通过引用泄露
- 成本和调用量可统计

### 阶段四：状态图和人工审批

目标：让复杂业务流程可编排。

建议任务：

- 将固定流程升级为显式状态图
- 支持节点级重试
- 支持人工确认节点
- 支持中断恢复
- 支持不同业务路由

验收标准：

- 查询类问题走普通 RAG
- 写操作工具必须人工确认
- 失败节点可以定位和重试
- 流程事件仍然能通过 SSE 展示

### 阶段五：再考虑多 Agent

目标：面向复杂业务场景拆分专业角色。

可选 Agent：

- 路由 Agent：判断问题类型
- 检索 Agent：负责查询改写和多路检索
- 回答 Agent：负责组织答案
- 审核 Agent：检查引用和合规风险
- 工具 Agent：处理订单、工单、库存等业务系统调用

验收标准：

- 多 Agent 拆分后质量明显提升
- 延迟和成本可接受
- 每个 Agent 有独立评测
- 每个 Agent 的输入输出可审计

## 5. 建议的近期开发清单

优先做下面这些，性价比最高：

1. 新增 RAG 评测集和评测脚本
2. 增加 hybrid search 的接口结构
3. 增加 rerank 服务抽象
4. 给 `Tool` 增加 schema、权限和超时字段
5. 给 `KnowledgeSearchTool` 增加 metadata filters
6. 扩展 Trace，记录检索结果、工具调用和模型耗时
7. 增加输出引用校验
8. 增加无资料拒答测试
9. 在前端知识库页面增加检索测试入口
10. 在前端 Agent 面板展示工具调用耗时和状态

## 6. 最终目标

后续理想状态不是“做一个能聊天的机器人”，而是形成一个企业内部可长期运营的知识与工具智能平台：

- 知识能管理
- 检索能评测
- 回答能追溯
- 工具能治理
- 权限能控制
- 行为能审计
- 成本能统计
- 流程能编排

这样项目才会从“演示型 RAG”真正升级成“企业级 Agent 应用”。
