# 知识库入库优化方案

本文档用于规划 `Enterprise RAG Assistant` 的知识库入库优化。目标不是单纯“把文件切块后写入 Milvus”，而是把企业资料加工成更适合检索、引用、权限控制和质量评测的知识资产。

## 1. 背景与判断

当前系统已经具备文档上传、解析、切分、Embedding、Milvus 入库和引用返回能力，但入库链路仍偏基础：

- 切分主要服务于向量检索，结构信息保留不足。
- 标题、章节、页码、表格、FAQ、标签等信息没有充分参与检索。
- 文档解析、切分、向量化、写入还缺少任务化和质量检查。
- 后续 query 改写、混合检索、rerank 的效果高度依赖入库质量。

企业级 RAG 的经验是：检索准确率很大一部分取决于入库质量。如果 chunk 切得不合理、元数据缺失、表格丢失或段落语义被切断，后续再强的 query rewrite 和 rerank 也只能在不理想的候选片段里补救。

## 2. 总体目标

入库优化要解决四个问题：

1. **可检索**：用户问法和文档表达不一致时，也能命中相关片段。
2. **可引用**：答案能返回清晰来源，包括文档、章节、页码或片段位置。
3. **可治理**：文档有知识库空间、部门、标签、密级、上传人等元数据。
4. **可评测**：入库后能测试召回效果，而不是等问答失败才排查。

推荐目标链路：

```text
上传文件
  -> 保存原文件和文档记录
  -> 解析文本、表格、图片 OCR、音频转写
  -> 清洗和结构化
  -> 按标题/段落/表格/FAQ 做语义切分
  -> 生成 chunk 元数据
  -> 生成 summary / keywords / possible_questions
  -> 生成 embedding
  -> 写入 Milvus / PostgreSQL
  -> 入库质量检查
  -> 可检索、可引用、可重建
```

## 3. 分层设计

### 3.1 原始文档层

保存用户上传或同步的原始资料，用于重解析、审计和原文跳转。

建议字段：

```text
documents
  id
  knowledge_base_id
  document_name
  source_type          file / url / wechat / api / manual
  source_path
  file_md5
  extension
  size_bytes
  owner_user_id
  department_id
  confidentiality     public / internal / confidential
  tags
  status              pending / parsing / embedding / indexed / failed
  created_at
  updated_at
```

当前 Milvus 中已有部分文档和 chunk 字段，后续可以先在 PostgreSQL 补文档表，再逐步把 metadata 同步到 Milvus 过滤字段。

### 3.2 解析结构层

解析结果不应只有纯文本，建议保留结构化节点。

```text
ParsedDocument
  title
  blocks[]

ParsedBlock
  block_id
  type                heading / paragraph / list / table / image_ocr / transcript / qa
  level               标题层级
  text
  page_number
  section_path        ["员工手册", "假勤制度", "年假"]
  order_index
```

这样做的好处：

- 切分时不容易切断标题和正文关系。
- 表格、列表、FAQ 可以按独立语义单元处理。
- 引用可以精确到章节和页码。
- 后续知识库详情页可以展示文档结构。

### 3.3 检索片段层

Chunk 是 RAG 检索和引用的核心单位。

建议每个 chunk 包含：

```text
chunks
  id
  document_id
  knowledge_base_id
  chunk_index
  chunk_type          section / paragraph / table / faq / transcript
  content
  title
  section_path
  page_start
  page_end
  parent_chunk_id
  summary
  keywords
  possible_questions
  token_count
  metadata_json
  embedding
  embedding_model
```

其中 `parent_chunk_id` 用于父子分块：小 chunk 用于精准召回，大 chunk 或章节用于回答上下文补全。

## 4. 切分策略

### 4.1 第一版策略

优先级从高到低：

1. 按 Markdown / Word / PDF 标题结构切分。
2. 按段落和列表保持语义完整。
3. 表格单独成 chunk，表格前后的说明文字可以合并进上下文。
4. FAQ 按“问题 + 答案”成 chunk。
5. 超长段落再按 token 长度递归切分。

建议参数：

```text
target_chunk_tokens = 500~800
max_chunk_tokens = 1200
overlap_tokens = 80~120
min_chunk_tokens = 80
```

切分时要避免：

- 只按字符数硬切。
- 标题和正文分离。
- 表格被切成几段后失去行列含义。
- 页眉、页脚、水印、目录重复进入 chunk。

### 4.2 父子分块

推荐在第二阶段引入父子分块：

```text
父 chunk：一个完整章节，1000~2500 tokens
子 chunk：章节内小段，300~800 tokens
检索：优先命中子 chunk
回答：取子 chunk + 父 chunk 摘要/邻近段落
引用：展示子 chunk 来源，必要时跳转父章节
```

这种方式适合制度、手册、产品文档。它能兼顾“检索精准”和“回答上下文完整”。

## 5. 检索辅助字段

为了提升召回，入库时可以为每个 chunk 生成辅助字段：

```text
summary              1~3 句摘要
keywords             关键词、别名、产品型号、制度编号、人名、部门名
possible_questions   用户可能会怎么问
```

示例：

```json
{
  "content": "员工工作满一年不满十年的，年休假为五天。",
  "summary": "该片段说明员工年休假的天数规则。",
  "keywords": ["年假", "年休假", "假勤制度", "满一年", "五天"],
  "possible_questions": [
    "工作满一年有几天年假？",
    "公司年休假怎么计算？",
    "员工入职多久可以休年假？"
  ]
}
```

第一版可以只生成 `keywords` 和 `summary`；`possible_questions` 可以在后续评测和召回优化时加入。

## 6. 元数据与权限

企业知识库必须把权限信息带入入库链路。建议 metadata 至少包含：

```text
knowledge_base_id
document_id
document_name
source_type
department_id
owner_user_id
confidentiality
tags
created_at
updated_at
page_start
page_end
section_path
```

后续检索时通过 metadata filter 限制范围：

```text
用户问题
  -> 计算用户可访问知识库和文档范围
  -> 检索时传入过滤条件
  -> sources 返回前二次校验权限
```

这比只在前端隐藏文档安全得多。

## 7. 入库任务化

当前上传链路可以继续保留同步版本，但建议新增异步任务模型：

```text
document_ingest_tasks
  id
  document_id
  task_type           parse / embed / reindex / rebuild
  status              pending / running / success / failed
  progress
  current_step
  error_message
  started_at
  finished_at
```

任务步骤：

```text
save_file
parse_document
clean_blocks
split_chunks
generate_metadata
generate_embeddings
write_vector_store
quality_check
mark_indexed
```

前端知识库页面可以展示每个步骤，方便维护人员知道失败在哪里。

## 8. 入库质量检查

入库完成后，不直接认为“可用”，而是做轻量检查：

- chunk 数量是否为 0。
- 平均 chunk 长度是否异常。
- 是否存在大量重复 chunk。
- 是否成功生成 embedding。
- metadata 是否包含 `document_id`、`document_name`、`chunk_index`。
- 用文档标题、章节标题、自动问题跑一次检索测试。

建议返回一个质量报告：

```json
{
  "document_id": "...",
  "chunk_count": 42,
  "avg_chunk_tokens": 620,
  "empty_chunk_count": 0,
  "duplicate_ratio": 0.03,
  "embedding_ready": true,
  "warnings": []
}
```

## 9. 与现有代码的落点

建议逐步改造，不推倒重来：

```text
backend/ai_service/knowledge/
  service.py                    保留现有上传编排
  parser_service.py              新增：解析为 ParsedDocument
  chunking_service.py            新增：结构化切分
  ingest_quality_service.py      新增：入库质量检查
  document_task_service.py       新增：任务状态

backend/ai_service/retrieval/
  vector_store.py                扩展 metadata 和 list/search 接口

frontend/next-web/components/knowledge/
  document-detail-drawer.tsx     展示 chunk、质量报告、重建入口
```

## 10. 分阶段实施

### 阶段一：结构化 chunk 和 metadata

- 保留现有上传接口。
- 优化切分逻辑，保留标题、章节、页码。
- chunk metadata 增加 `section_path`、`chunk_type`、`tags`。
- 知识库详情页展示 chunk 列表和基础质量信息。

验收标准：

- 同一份制度文档能按章节召回。
- sources 中能看到文档名、章节、片段序号。
- 上传后能查看 chunk 内容。

### 阶段二：检索辅助字段

- 入库时生成 summary 和 keywords。
- 检索时把 `content + title + keywords` 作为可检索文本。
- 为 FAQ、制度、产品手册分别优化切分模板。

验收标准：

- 用户用口语问法时，召回结果比原始版本更稳定。
- 产品型号、制度编号、人名等精确词不丢失。

### 阶段三：异步任务和质量检查

- 新增入库任务表。
- 前端展示解析、切分、向量化、写入状态。
- 支持单文档重解析、重切分、重建索引。
- 生成入库质量报告。

验收标准：

- 大文件上传不阻塞用户界面。
- 入库失败能定位到具体步骤。
- 可以单文档重建，不需要全库重建。

### 阶段四：父子分块和评测闭环

- 引入 parent/child chunk。
- 构建固定检索评测集。
- 每次改切分策略后跑召回评测。

验收标准：

- TopK 命中率、引用准确率有可量化报告。
- 长制度、长手册的回答上下文更完整。

## 11. 推荐优先级

近期优先做：

1. 结构化切分。
2. chunk metadata 补齐。
3. 入库质量检查。
4. 知识库页面增加 chunk 查看和检索测试。
5. 再接 query rewrite、hybrid search、rerank。

一句话总结：

> 入库优化的核心是把文件加工成“模型容易检索、用户容易溯源、系统容易治理”的知识单元。只有入库质量稳定，后面的 query 改写和重排序才有真正发挥空间。
